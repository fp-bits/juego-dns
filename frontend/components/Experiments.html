Experimentos guiados: Estos 3 experimentos explican algunos conceptos básicos de DNS y cómo funciona el sitio.

1. Crear un registro A

Vamos a crear el registro DNS más básico: un registro A. Para la dirección IP, usaremos una IP (213.188.218.160) que configuré para este proyecto y que simplemente muestra una imagen de una naranja.

  1. Crea un registro con estos datos:
    • Nombre: orange
    • Tipo: A
    • Dirección IPv4: 213.188.218.160
    • TTL: 60
    En esta página, los valores de TTL siempre se expresan en segundos.
  2. Pulsa «Crear».
  3. Visita en el navegador.
  4. ¡Deberías ver un sitio web con una imagen de una naranja!

2. Crear un registro CNAME

Vamos a crear un registro CNAME que apunte indirectamente a la misma dirección IP de la naranja.

  1. Crea un registro con estos datos:
    • Nombre: fruit
    • Tipo: CNAME
    • Destino: orange.jvns.ca
    • TTL: 60
  2. Pulsa «Crear».
  3. Visita en el navegador.
  4. ¡Deberías ver un sitio web con una imagen de una naranja!

3. Ver cómo funcionan los registros CNAME

En la sección «Solicitudes», al final de esta página, puedes ver todas las solicitudes DNS de los subdominios de {{ domain}}.messwithdns.com. Veamos el registro CNAME que creamos en el experimento anterior para entender cómo funcionan estos registros.

  1. Busca la sección «Solicitudes» al final de la página. Deberías ver una solicitud para .
  2. Mira el nombre que aparece en «Desde». ¿Lo reconoces? Podría ser tu proveedor de Internet o un resolvedor DNS público como Cloudflare o Google.
  3. Observa el tipo de la solicitud y de la respuesta. Verás que se solicita un registro A, pero el servidor DNS responde con un registro CNAME.

Experimentos curiosos: En estos 5 experimentos rompemos cosas para divertirnos y aprender.

1. Visitar un dominio antes de crear su registro DNS

¿Sabías que con solo visitar un dominio puedes hacer que deje de funcionar? ¡Es raro, pero cierto! En este experimento:

  • Crearemos un registro DNS para un subdominio y luego lo visitaremos (¡funcionará!).
  • Visitaremos un subdominio, crearemos su registro DNS y volveremos a visitarlo (¡no funcionará!).
¡Empecemos!

  1. Crea un registro CNAME con estos datos:
    • Nombre: visit-after
    • Tipo: CNAME
    • Destino: orange.jvns.ca
    • TTL: 3600
  2. Visita en el navegador. Deberías ver el sitio de la naranja: ¡todo funciona!
  3. Ahora visita en el navegador. Deberías ver un error como «No se encuentra el servidor», porque todavía no hemos creado el registro.
  4. Crea un registro CNAME con estos datos:
    • Nombre: visit-before
    • Tipo: CNAME
    • Destino: orange.jvns.ca
    • TTL: 3600
  5. Vuelve a visitar en el navegador. Deberías obtener el mismo error «No se encuentra el servidor», incluso si fuerzas la recarga de la página.

¿Por qué aparece el error «No se encuentra el servidor»?

Esto es lo que ocurre con «visit-after», donde todo funciona como debería:

  • Creas el registro
  • El navegador pregunta: ¿dónde está visit-after.{{domain}}.messwithdns.com?
  • El servidor DNS responde: ¡correcto!

«visit-before» no funciona por algo que hacen los resolvedores DNS llamado almacenamiento en caché negativo, que consiste en guardar en caché la ausencia de un registro.

  • Navegador: ¿dónde está visit-before.{{domain}}.messwithdns.com?
  • Servidor DNS: ¡no existe!
  • Resolvedor DNS: «¡Vaya, no existe! Mejor lo guardo en caché»
  • Resolvedor DNS: no existe
  • Creas el registro
  • Solicitud: ¿dónde está visit-before.{{domain}}.messwithdns.com?
  • Resolvedor DNS: «¡Ya consulté esto! ¡No existe!»
  • Resolvedor DNS: no existe
  • Tú: :( :( :( ¡PERO SÍ EXISTE!
  • Esperas 1 hora y vuelves a probar; todo funciona porque la caché caducó

Al final no apareció el error «No se encuentra el servidor»...

No todos los resolvedores DNS almacenan respuestas negativas en caché. Por ejemplo, Cloudflare no lo hace, así que este experimento no funcionará si usas el DNS de Cloudflare.

2. Configurar un TTL muy largo

Configurar un TTL muy largo (por ejemplo, de 10 días) resulta muy incómodo: si quieres hacer un cambio, tendrás que esperar hasta 10 días para que se aplique. Vamos a:

  • Crear un registro con un TTL corto, visitar la página, cambiar el registro y actualizarla. ¡Veremos el cambio!
  • Crear un registro con un TTL largo, visitar la página, cambiar el registro y actualizarla. ¡No veremos el cambio!

Empecemos con el TTL corto.

  1. Crea un registro CNAME con estos datos:
    • Nombre: short-ttl
    • Tipo: CNAME
    • Destino: orange.jvns.ca
    • TTL: 30
  2. Visita en el navegador. Deberías ver el sitio de la naranja.
  3. Pulsa «Editar» y cambia el registro CNAME para que apunte a purple.jvns.ca.

  4. Vuelve a visitar en el navegador. Puede que tengas que forzar la actualización con Ctrl+Shift-R/Cmd+Shift+R, pero ahora deberías ver el sitio morado. ¡La actualización funcionó!

    Ahora veamos qué ocurre al configurar un TTL largo.

  5. Crea un registro CNAME con estos datos:
    • Nombre: long-ttl
    • Tipo: CNAME
    • Destino: orange.jvns.ca
    • TTL: 3000000 (¡son 30 días! También puedes usar cualquier número bastante grande)
  6. Visita en el navegador. Deberías ver el sitio de la naranja.
  7. Pulsa «Editar» y cambia el registro CNAME para que apunte a purple.jvns.ca.
  8. Vuelve a visitar en el navegador. Deberías ver el mismo sitio de la naranja: ¡no ha cambiado! Esto se debe a que el registro DNS anterior sigue guardado en caché. También puede que notes que no hay solicitudes nuevas en la sección «Solicitudes».

¿Qué ocurre cuando configuro un TTL largo o corto?

Cuando el TTL es de 30 segundos, la segunda vez que haces la solicitud, la caché ya habrá caducado y recibirás la versión nueva. Este es el proceso detallado:

  • Creas un registro
  • El navegador pregunta: ¿dónde está short-ttl.{{domain}}.messwithdns.com?
  • El resolvedor no lo tiene en caché, así que lo solicita
  • El servidor DNS responde: ¡Aquí está la IP! ¡El TTL es de 30 segundos!
  • El resolvedor guarda la IP en caché durante 30 segundos
  • El resolvedor responde: ¡Aquí está la IP!
  • ... pasan 30 segundos
  • Actualizas el registro
  • El navegador pregunta: ¿dónde está short-ttl.{{domain}}.messwithdns.com?
  • El resolvedor detecta que la caché caducó y vuelve a solicitarlo
  • El servidor DNS responde: ¡Aquí está la IP!
  • El resolvedor guarda la IP en caché durante 30 segundos
  • El resolvedor responde: ¡Aquí está la IP nueva!

Cuando el TTL es un número grande, como 10 días, la caché no caduca y no puedes recibir el sitio actualizado. Esto es lo que ocurre:

  • Creas un registro
  • El navegador pregunta: ¿dónde está long-ttl.{{domain}}.messwithdns.com?
  • El resolvedor no lo tiene en caché, así que lo solicita
  • El servidor DNS responde: ¡Aquí está la IP! ¡El TTL es de 10 días!
  • El resolvedor guarda la IP en caché durante 10 días
  • El resolvedor responde: ¡Aquí está la IP!
  • ... pasan 30 segundos
  • Actualizas el registro
  • El navegador pregunta: ¿dónde está long-ttl.{{domain}}.messwithdns.com?
  • El resolvedor responde: ¡Ya lo tengo en caché! ¡Aquí está la IP!

3. Apuntar a example.com

¿Sabías que al apuntar 2 dominios distintos a la misma dirección IP puedes ver páginas diferentes al visitar cada uno? Vamos a:

  • Apuntar tu dominio a la misma IP que example.com.
  • Obtener un error 404 (distinto de lo que ocurre al visitar example.com).
¡Empecemos!

  1. Visita example.com en el navegador. Fíjate en que no aparece un error 404.
  2. Busca la dirección IP de example.com. Para ello, ejecuta dig +short example.com en la terminal. También puedes hacer como si lo hubieras ejecutado: la IP es 93.184.216.34 :).
  3. Crea un registro A con estos datos:
    • Nombre: bad-ip
    • Destino: 93.184.216.34
    • TTL: el que quieras
  4. Visita en el navegador. Deberías obtener un error 404 (no encontrado).
¿Por qué aparece un error 404?

Cuando el navegador solicita un sitio web, envía una cabecera Host con el nombre del dominio que escribiste. Si el servidor (como Apache/nginx) no reconoce ese nombre, suele responder con un error 404. Aquí tienes más detalles.

Cuando solicitas example.com y todo funciona, esto es lo que ocurre:

  • Escribes example.com en el navegador
  • El navegador pregunta: ¿dónde está example.com?
  • El resolvedor responde: 93.184.216.34
  • Navegador (a 93.184.216.34): ¡una solicitud HTTP para Host: example.com!
  • Servidor de example.com: ¡conozco ese sitio! ¡Aquí tienes una respuesta!

Pero cuando solicitas bad-ip.{{domain}}.messwithdns.com y obtienes un 404, esto es lo que ocurre:

  • Escribes http://bad-ip.{{domain}}.messwithdns.com en el navegador
  • El navegador pregunta: ¿dónde está bad-ip.{{domain}}.messwithdns.com?
  • El resolvedor responde: 93.184.216.34
  • (¡hasta aquí todo es igual!)
  • Navegador (a 93.184.216.34): ¡una solicitud HTTP para Host: bad-ip.{{domain}}.messwithdns.com!
  • Servidor de example.com: ¡Nunca he oído hablar de ese sitio! ¡404!

4. Convencer a 3 servidores DNS de que tu subdominio tiene 3 IP distintas (3-ips)

¿Sabías que distintos resolvedores DNS pueden tener información contradictoria sobre la dirección IP de tu dominio? Normalmente esto es un problema, pero vamos a provocarlo a propósito para que veas cómo podría ocurrir por accidente.

Vamos a convencer a:

  • el servidor DNS de Google de que tu subdominio tiene una IP (10.11.12.13);
  • el servidor DNS de Cloudflare de que tiene otra IP (20.21.22.23);
  • el servidor DNS de Quad9 de que tiene una tercera IP (30.31.32.33).

¡Empecemos!

  1. Crea un registro A con estos datos:
    • Nombre: 3-ips
    • Destino: 10.11.12.13
    • TTL: 3600
    Necesitamos un TTL bastante largo para que los resolvedores guarden la IP en caché durante todo el experimento.
  2. Ejecuta esto en la terminal: 
    $ dig +noall +answer @8.8.8.8 3-ips.{{domain}}.messwithdns.com
    Ejecútalo 10 veces para asegurarnos. Google tiene muchos servidores DNS, así que queremos consultar la mayoría.
  3. Cambia el registro A para que apunte a 20.21.22.23. Mantén el mismo TTL.
  4. ¡Es hora de informar a Cloudflare sobre el dominio! Ejecuta esto en la terminal: 
    $ dig +noall +answer @1.1.1.1 3-ips.{{domain}}.messwithdns.com
    Ejecútalo varias veces.
  5. ¡Último cambio! Cambia el registro A para que apunte a 30.31.32.33. Mantén el mismo TTL.
  6. Ahora informaremos a Quad9 sobre el dominio. Ejecuta esto en la terminal: 
    $ dig +noall +answer @9.9.9.9 3-ips.{{domain}}.messwithdns.com
  7. Ahora preguntemos a los 3 proveedores qué dirección IP creen que tenemos. Esto es lo que veo: 
    $ dig +noall +answer @8.8.8.8 3-ips.{{domain}}.messwithdns.com
3-ips.ionized-twig.messwithdns.com. 30	IN A	10.11.12.13
$ dig +noall +answer @1.1.1.1 3-ips.{{domain}}.messwithdns.com
3-ips.ionized-twig.messwithdns.com. 30	IN A	20.21.22.23
$ dig +noall +answer @9.9.9.9 3-ips.{{domain}}.messwithdns.com
3-ips.ionized-twig.messwithdns.com. 30	IN A	30.31.32.33
    ¡Los 3 servidores DNS tienen opiniones distintas sobre nuestra dirección IP! Misión cumplida.

¿Por qué funciona?

Esto funciona porque Google, Cloudflare y Quad9 nunca buscan nuestro dominio de forma proactiva: solo lo consultan cuando alguien hace una solicitud. Y como eres literalmente la única persona del mundo que ha solicitado 3-ips.{{domain}}.messwithdns.com, tienes el control total sobre cuándo conocen el dominio por primera vez.

Al final Google me dio 30.31.32.33, no 10.11.12.13. ¿Por qué?

8.8.8.8 no es un solo servidor, sino muchos servidores DNS. Lo más probable es que, al consultar 8.8.8.8 por primera vez, no llegaras a algunos de sus servidores. Al final, llegaste a un servidor nuevo que aún no había guardado el registro en caché. (Por eso se indica «consultar 10 veces», aunque a veces 10 no sean suficientes).

5. Configurar dos registros A en conflicto

Muchos dominios tienen asociadas varias direcciones IP. Normalmente no lo notas porque ambas direcciones IP sirven exactamente la misma página. Pero podemos ver cómo funciona si usamos dos IP que sirven sitios totalmente distintos.
  • Crea 2 registros que apunten a páginas diferentes (una naranja y otra morada).
  • Usa curl para solicitar repetidamente el mismo dominio y observa qué ocurre.
  1. Crea un registro A con estos datos:
    • Nombre: conflict
    • Dirección IPv4: 213.188.218.160
    • TTL: 5
  2. Crea otro registro A con estos datos:
    • Nombre: conflict
    • Dirección IPv4: 213.188.209.192
    • TTL: 5
  3. Ejecuta esto en la terminal: 
    curl http://conflict.{{currDomain()}}.messwithdns.com 2>/dev/null | grep title
    10 veces. Cuando lo ejecuto, el resultado alterna entre «orange» y «purple», como aquí. Puede que tú veas otro comportamiento; lo explicaremos más adelante :). 
    $ curl http://conflict.{{currDomain()}}.messwithdns.com/ 2> /dev/null | grep title
<title>orange</title>
$ curl http://conflict.{{currDomain()}}.messwithdns.com/ 2> /dev/null | grep title
<title>purple</title>
$ curl http://conflict.{{currDomain()}}.messwithdns.com/ 2> /dev/null | grep title
<title>orange</title>
$ curl http://conflict.{{currDomain()}}.messwithdns.com/ 2> /dev/null | grep title
<title>purple</title>
$ curl http://conflict.{{currDomain()}}.messwithdns.com/ 2> /dev/null | grep title
<title>orange</title>
$ curl http://conflict.{{currDomain()}}.messwithdns.com/ 2> /dev/null | grep title
<title>purple</title>
$ curl http://conflict.{{currDomain()}}.messwithdns.com/ 2> /dev/null | grep title
<title>orange</title>
$ curl http://conflict.{{currDomain()}}.messwithdns.com/ 2> /dev/null | grep title
<title>purple</title>
¡No logra decidir qué sitio web mostrar!

¿Por qué distintas personas obtienen resultados diferentes en este experimento?

He visto 3 resultados diferentes en este experimento. ¿Por qué? Empecemos por pensar qué ocurre cuando ejecutas curl.

  • Creas 2 registros
  • Ejecutas curl conflict.{{domain}}.messwithdns.com
  • curl realiza una solicitud DNS
  • El resolvedor encuentra 2 registros coincidentes
Ahora el resolvedor tiene 2 registros y debe decidir en qué orden devolverlos. Puede:
  • Devolver los registros en el mismo orden en que los recibió.
  • Cambiar el orden cada vez que recibe una solicitud (¡eso es lo que hace el mío!).
  • Elegir un orden al azar.
  • ¡Quizá hacer algo más que no haya mencionado! ¡No lo sé!
Luego curl elige el primer registro de la respuesta, que depende del orden elegido por el resolvedor.

Experimentos prácticos: El resto de los experimentos son cosas que quizá quieras hacer en la vida real. Son más bien retos que tutoriales: cada uno tiene un breve resumen. ¡Anímate a explorar por tu cuenta! :)

1. Configurar un sitio web

Puedes usar el servicio que quieras para este experimento, como Netlify, GitHub Pages, GitLab Pages, etc. Estos son los pasos de ejemplo con Netlify:

  1. En Netlify: crea un sitio nuevo.
  2. En Netlify: añade el dominio www.{{currDomain()}}.messwithdns.com a tu sitio.
  3. En Mess With DNS: crea un registro CNAME que apunte www.{{currDomain()}}.messwithdns.com a tu nuevo sitio de Netlify.
  4. Visita www.{{currDomain()}}.messwithdns.com en el navegador y comprueba si funciona.

Los registros DNS se eliminan después de una semana, ¡así que no uses este sitio para nada importante! :)

2. Recibir un correo electrónico

Puedes usar cualquier servicio de correo que permita utilizar tu propio dominio. Aquí tienes los pasos de ejemplo con Fastmail (aunque hace mucho que no se prueban y quizá no funcionen):

  1. En Fastmail: regístrate para obtener una prueba gratuita con el correo you@mail.{{currDomain()}}.messwithdns.com.
  2. En Mess With DNS: crea 2 registros MX que apunten mail.{{currDomain()}}.messwithdns.com a los servidores de correo de Fastmail. Fastmail te dará instrucciones al registrarte.
  3. Envíate un correo a you@mail.{{currDomain()}}.messwithdns.com y comprueba si lo recibes.

Los registros DNS se eliminan después de una semana, ¡así que no uses esta dirección de correo para nada importante! :)

3. Hacer que pasen los registros SPF y DKIM de tu correo

El objetivo es crear registros SPF y DKIM para que los destinatarios reconozcan que tu correo procede de tu dominio.

  1. Primero tienes que configurar una cuenta de correo, como se describe en el experimento 2.
  2. Prueba tus registros SPF siguiendo las instrucciones de esta página de prueba de SPF.
  3. En Fastmail: sigue sus instrucciones para configurar SPF y DKIM.
  4. Vuelve a probar tus registros SPF y comprueba que funcionan. La página de prueba de SPF explica cómo hacerlo.
